# Validation sweep: 0.6.0 against the legacy production transcripts

The quality harness (`tools/quality_harness/`) answered whether the 0.6.0 decode and
alignment changes are right, on six files, inside the production image. This sweep
answers a different question on a hundred: does the release hold or improve on what the
service has actually been publishing for the last eighteen months, across the whole
range of material the archive contains.

It runs against an isolated copy of the service and never touches production. See
"Isolation" below; that constraint is the reason for every path in the commands.

## What the legacy baseline actually is

The baseline comes from `sermon_metadata.english_transcription` in the orchestrator's
`sermon_orchestrator.db`, read from a copy, joined to the audio archive on the basename
of `orig_audio_url`. The join is exact: 655 rows, 655 audio files, no orphans either
way. 653 rows carry a transcript; two are empty because the orchestrator's re-run lost
the submission five times and gave up.

Two things about that baseline change how the comparison has to be read, and both were
found by measuring rather than assumed.

**It is not one code version.** Bucketing each row by when its
`GenerateEnglishTranscription` step completed, against the release tag dates, splits the
653 into four eras:

| era | rows | dates | code |
|---|---|---|---|
| E1 | 531 | 2025-03-06 to 2025-03-09 | 0.1.5: one `model.transcribe(beam_size=7, best_of=7)`, no prompt, no denoise |
| E2 | 91 | 2025-03-20 to 2026-06-27 | 0.2.1/0.2.2: five passes, scalar temperature, single-speaker prompt |
| E3 | 21 | 2026-06-28 to 2026-09-06 | 0.3.0/0.3.1: as E2 plus the always-on denoise stage |
| E4 | 10 | 2026-09-07 | 0.4.0 to 0.5.4: the fixed code, not legacy output at all |

E3 is the only era with the full defect set described in `docs/SESSION_KNOWLEDGE.md`.
Averaging all four together would compare 0.6.0 against a blend of four different
services, so the analyzer reports every table per era as well as overall.

**The collapses are not in it.** The 0.15 to 1.24 words-per-second collapses recorded in
the session knowledge do not survive anywhere in the database. The lowest legacy rate
across all 653 rows is 1.79 wps and the next is 1.98; the distribution is
p5 2.46, median 2.75, p95 2.98. The twelve 2024 teachings that collapsed are absent from
the 2026-06-24 database backup and present in the current file with
`GenerateEnglishTranscription` completion times of 2026-09-07 06:31 to 08:02, which is
after the 0.4.0 fix was deployed. In other words their collapsed text was overwritten by
the 0.5.4 re-run before this sweep was designed, and no earlier copy of it exists: the
June 2026 backups do not contain those rows, and every row they do contain is
byte-identical to the current file.

So the sweep cannot measure "does 0.6.0 fix the collapses" against stored legacy text.
What it can do, and what the file list is built for:

- For the ten re-run files, the baseline is 0.5.4 output. That comparison asks whether
  0.6.0 holds the ground 0.4.0 already took on exactly the material that broke.
- For the two files with no transcript at all, there is no baseline; they are carried in
  `supplementary` so the run proves the release can transcribe them.
- For everything else the question is the one that matters in production: does 0.6.0
  hold or improve on what is published today.
- The analyzer still computes a data-driven low-rate split (`choose_wps_split`) rather
  than assuming a cutoff, and reports the method it used. On this baseline it will report
  no natural gap, which is itself the finding.

## The hundred files

`file_list.json` is generated by `select_files.py` and committed. The selection is
deterministic: every tie breaks on the filename and the single shuffle is seeded.

Mandatory rules first, then a stratified fill:

| rule | files | why |
|---|---|---|
| `rerun_2026_09_07` | 10 | the known collapses, now carrying 0.5.4 baselines |
| `defective_era_E3` | 21 | every row produced by the code with all four defects live |
| `below_vad_cutover` | 20 | every file under -26 dBFS: the whole 0.35 VAD branch |
| `harness_reference` | 6 | the files every acceptance threshold is stated against |
| `lowest_legacy_wps` | 10 | the bottom of the legacy rate distribution |
| `lowest_bitrate` | 10 | 34 to 47 kbps, where the decode has least to work with |
| `very_long` | 13 | every recording over 2700 s |
| `non_mono_or_non_mp3` | 7 | the six stereo files and the one AAC file |
| `multi_voice` | 12 | classes, retreats, men's breakfasts, Q&A |
| `rare_sample_rate` | 2 | the 32 kHz encoder path, five files in the archive |
| `cutover_zone` | 12 | spread evenly across -26 to -24 dBFS |
| `stratified_fill` | 10 | a seeded draw over duration x level cells |

Rules overlap, so the counts sum past 100; the list itself is 100 distinct files plus 2
supplementary. Resulting strata:

- duration: 30 short (under 900 s), 39 medium, 18 long, 13 very long (over 2700 s)
- level: 2 very quiet, 18 quiet, 16 at -26 to -24, 10 at -24 to -22, 40 normal, 14 loud
- VAD branch as shipped: 20 files on 0.35, 80 on 0.5
- bit rate: 12 very low (under 50 kbps), 36 low, 32 medium, 20 high
- sample rate: 24 at 22.05 kHz, 23 at 44.1 kHz, 51 at 48 kHz, 2 at 32 kHz
- channels: 94 mono, 6 stereo
- legacy era: 51 E1, 18 E2, 21 E3, 10 E4
- 12 multi-voice recordings

The level strata are the point of the exercise for the VAD question. The 0.6.0 rule
switches VAD threshold at -26 dBFS on the strength of two files, one at -24.5 that
worked and one at -28.6 that failed. This sample puts 20 files below the cut and 26
within 2 dB above it, and the analyzer's level table reports one row per decibel, so the
edge can be moved on measured rows.

## Isolation

The sweep must not perturb production. The rules are absolute:

- The `transcription-api` container on port 5030 is never stopped, restarted, rebuilt,
  exec'd into or sent traffic.
- The sweep runs as `transcription-api-sweep` on port 5031 with its own `DB_FILE`,
  `UPLOAD_FOLDER` and `MFA_ROOT_DIR`, all under `/home/jay/sweep/`.
- `/home/jay/SourceCode/TranscriptionAPI` (the deploy checkout) and the production `tmp`
  bind mount are never mounted or written.
- The orchestrator database is copied first and the copy is opened read-only.
- GPU 0 is shared with production and cannot be avoided, so the run needs at least 4 GB
  free before it starts and its wall-clock numbers are not benchmark quality. Contention
  cuts both ways and is expected.

The container the sweep talks to:

```
docker run -d --name transcription-api-sweep --gpus device=0 -p 5031:5000 \
  -e DB_FILE=/data/sweep.db \
  -e UPLOAD_FOLDER=/data/uploads \
  -e MFA_ROOT_DIR=/data/mfa_root \
  -v /home/jay/sweep/service:/data \
  transcription-api:<tag>
```

`run_sweep.sh <tag>` does all of that, with the guards, and then runs the sweep and the
analysis. One trap it handles: a private `MFA_ROOT_DIR` must be seeded with the image's
pretrained models. MFA resolves `english_mfa` under `$MFA_ROOT_DIR/pretrained_models`, so
pointing the variable at an empty directory makes every alignment fail with "Could not
find a model named english_mfa for acoustic" while the job still completes on Whisper
timings and reports `mfa_applied=false`. The 90 MB model directory is copied out of the
image once.

The service runs as root, so the uploaded copy of each file and the `_aligned` directory
it writes are root-owned inside root-owned directories: the runner, running as the login
user, cannot unlink them and its per-job cleanup is best effort. `run_sweep.sh` clears
them at the end with a throwaway container on the same volume. The uploaded copies of
the whole hundred come to 1.6 GB, and the transient 16 kHz WAV MFA is given is deleted by
the service after each job, so this is tidiness rather than a disk risk on 39 GB free.

## Running it

Three steps, all from the repo root on the GPU host with `tools/quality_sweep/` copied
across.

Rebuild the baseline (only needed if the archive or the database changes):

```
cp /home/jay/SourceCode/SermonOrchestrator/data/sermon_orchestrator.db /home/jay/sweep/legacy.db
python3 extract_legacy.py --db /home/jay/sweep/legacy.db \
    --audio-dir /home/jay/SourceCode/SermonPreprocessorAPI/data/audiofiles \
    --durations /home/jay/sweep/durations.csv --out /home/jay/sweep/legacy_baseline.json
python3 select_files.py --durations durations.csv --levels levels.csv \
    --baseline legacy_baseline.json --out file_list.json
```

`levels.sh` measures `levels.csv`: mean and max level in dBFS from
`ffmpeg -af volumedetect` plus codec, sample rate, channels and bit rate from ffprobe,
over the whole of each of the 655 files, niced and six at a time so it cannot compete
with production.

Run the sweep. It is resumable: `state.json` records the outcome of every finished file
and a rerun skips those. A quarantined, errored or timed-out job is recorded with its
reason and the runner moves on.

```
python3 runner.py --file-list file_list.json \
    --audio-dir /home/jay/SourceCode/SermonPreprocessorAPI/data/audiofiles \
    --base-url http://127.0.0.1:5031 --out-dir /home/jay/sweep/run
```

Analyse:

```
python3 analyze.py --results /home/jay/sweep/run/state.json \
    --baseline /home/jay/sweep/legacy_baseline.json --file-list file_list.json \
    --out-json /home/jay/sweep/analysis.json --out-md /home/jay/sweep/report.md
```

### What 0.6.0 adds, and what the analysis does with it

The decode is one beam-5 pass with a temperature ladder. A rescue pass fires only when
the primary shows an anomaly, re-decodes once with previous-text conditioning off, and is
kept only if it retains at least 99 percent of the primary's words. `analyze.py` reports
the firing rate, the selection rate, and every selected rescue with the word delta it
produced.

VAD is a level-selected profile rather than one threshold: the loud profile uses 0.5 with
a 1000 ms minimum silence and a hallucination filter, the quiet profile keeps the gentler
older parameters because 1000 ms of minimum silence shreds quiet audio. The level table
therefore carries words, segment count and mean segment length per decibel, and
`cutover_view` aggregates either side of -26 dBFS and inside the band straddling it. A
profile that is shredding a file shows as a collapse in mean segment length and a jump in
segment count, which is what 0.5 did to the retreat file before the profiles existed.

The decode is not bit-reproducible on longer files, and the rescue trigger is a threshold
on anomaly counts, so a run-to-run flip could change whether a file takes the rescue path.
`run_sweep.sh` submits five files spanning 238 s to 3388 s a second time into
`/home/jay/sweep/repeat`, and `determinism.py` pairs the two runs:

```
python3 determinism.py --run-a /home/jay/sweep/run/state.json \
    --run-b /home/jay/sweep/repeat/state.json \
    --out-json /home/jay/sweep/determinism.json --out-md /home/jay/sweep/determinism.md
```

The runner records every key `/status` returns, so the additive 0.6.0 fields
(`anomaly_count`, `anomaly_windows`, `flagged_segments`, `rescue_attempted`,
`rescue_selected`) land in the results without a code change here. The analyzer
distinguishes a field that is absent from one that is zero, so running against a 0.5.x
image reports the new fields as absent rather than as clean.

## Files

| file | what it is |
|---|---|
| `run_sweep.sh` | starts the isolated service with every guard, runs the sweep, analyses it |
| `levels.sh` | measures `levels.csv` over the archive with volumedetect and ffprobe |
| `extract_legacy.py` | builds `legacy_baseline.json` from a read-only copy of the orchestrator database |
| `strata.py` | bucket boundaries, era mapping, the VAD rule, and the three input readers |
| `select_files.py` | the selection rules; regenerates `file_list.json` |
| `file_list.json` | the committed 100-file sample with every stratum label and reason |
| `runner.py` | submit, poll, record; resumable, stdlib only |
| `analyze.py` | joins results to the baseline, writes the report and the results JSON |
| `determinism.py` | pairs two runs of the same files: word, anomaly and rescue-decision spread |
| `legacy_eras.py` | single-pass against multi-pass legacy words per second, raw and stratified |
| `norm.py` | the harness's word normalisation, so both sides normalise identically |

`tests/test_quality_sweep.py` covers the stratum boundaries, the selection rules, and
every piece of the analyzer's arithmetic against small fixtures.
